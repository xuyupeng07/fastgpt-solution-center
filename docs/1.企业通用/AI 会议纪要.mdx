## 一、场景洞察与痛点

### 1.1 为什么会议纪要值得做 AI

开会人人有份，纪要却人人推诿——这是组织里最典型的一块"高频、刚需、却没人愿意干"的活。多数企业不是没有工具：飞书、钉钉、腾讯会议都带了"AI 纪要"，看似已经解决了。但真正用起来才发现，这些平台自带的纪要功能**只解决了"转写"这一件事，没解决"沉淀、定制、跟进"这三件更要命的事**：免费额度有限、超出就要按用量订阅，纪要格式固定、不能按企业的模板和颗粒度输出，数据沉淀在单一 IM 平台里、接不进自己的 CRM 和项目管理。这正是 AI 能补上的空位——不是再做一个转写工具，而是把"听 → 整理 → 分发 → 跟进"整条链自动化。

### 1.2 共性痛点因链

| 现象 | 影响谁 | 根因 |
|------|--------|------|
| 会后纪要没人写、写出来拖几天 | 会议组织者加班；决策无法落地 | 纪要靠人回听录音、凭记忆整理，费时又易漏 |
| 口头待办散会后被忘掉、记岔 | 项目负责人、执行人 | 结论和行动项留在语音和聊天里，没有结构化沉淀 |
| 各平台自带纪要"不够用" | 采购、IT | 免费额度有限、进阶订阅贵，格式固定难定制，数据单平台沉淀难打通 |

三大根因层层递进：**转写有人做、整理没人做 → 待办没处落 → 沉淀与定制受限**。解决方案的全部模块都从这里长出来——下面第二章会逐一对应消灭，不留悬空痛点。

### 1.3 适用条件

本方案适合具备以下条件的组织，条件越充分、收益越显著：

- 会议高频、纪要负担重（每周多场跨部门/项目会议，纪要整理占人）；
- 已经使用飞书 / 钉钉 / 企业微信等办公入口，且对纪要的格式、颗粒度、系统联动有定制需求；
- 有明确的项目管理 / 任务系统（如 Jira、Teambition、TAPD 或自研），供行动项落地；
- 有明确的纪要负责人或制度（AI 不替人拍板，必须有人对纪要内容负责）。

> 若会议极少、或对纪要没有格式与联动要求，平台自带纪要已够用，无需启动智能化——这也是对客户负责的做法。

## 二、解决方案设计

### 2.1 总体蓝图

先看现状——断点都卡在"靠人回听、靠记忆整理、靠聊天记录追"上：

```mermaid
    C --> D["口头待办散在语音和聊天里"]
    D --> E["纪要拖延、待办遗漏"]
```

```mermaid

    C --> D["结构化纪要：结论/议题/行动项/负责人"]
    D --> E["按角色分发到项目/任务系统"]
    E --> F["待办持续跟进、纪要沉淀回知识库"]
```

### 2.2 多渠道 × 多系统覆盖

同一套转写与结构化流程在背后复用，成员从哪个入口进来都能拿到纪要：

| 入口/系统 | 接入方式 | 场景 |
|------|------|------|
| 飞书 / 钉钉 / 企业微信机器人 | OpenAPI 接入 | 会议结束把录音/文字丢进群，AI 回一段纪要 |
| 微信公众号 / 微信个人号 | API / ClawBot | 私域触达、出差途中口述纪要要点 |
| 小程序 / APP / 自研系统 | API 接入 | 业务后端、移动端发起纪要整理 |
| Web 免登录窗口 / 门户 | 分享链接 / iframe / 登录门户 | 团队统一入口、会后自助生成纪要 |
| Jira / Teambition / TAPD / 自研项目与任务系统 | API / 插件对接 | 行动项自动落成任务，持续跟进 |

> 两个维度分开看，缺一不可：**渠道**是「纪要从哪进来、从哪看」（飞书/钉钉/企微/Web/API），解决入口覆盖；**系统**是「AI 要把行动项送到哪」（项目/任务/知识库），解决业务打通。只有渠道没有系统，行动项还是没人跟；只有系统没有渠道，成员不知道从哪发起。

落到一个具体画面：产品经理在钉钉群里把会议录音丢给机器人，几十秒后拿到一份按"结论 / 行动项 / 负责人 / 截止时间"分好段的纪要，行动项自动落进 TAPD 变成待办，成员在飞书里也能看到同一份纪要——两个入口、两套后端，背后是同一套结构化流程。

### 2.3 痛点一一对应解决（因果闭环）

四个模块不是功能堆叠，而是一条链：**语音转写 → 结构化纪要 → 待办抽取 → 分发跟进**。每个模块都在消灭一个具体痛点，落地后变成一个可观察的结果：

| 客户痛点（脱敏） | 方案模块 | 落地后的结果 |
|------|---------|------------|
| 纪要靠回听录音、凭记忆整理 | ① 语音转写 + 结构化 | 会议结束一键生成纪要，整理约 30 分钟 → 3 分钟以内 |
| 口头待办散落、事后追忆 | ② 行动项自动抽取 | 结论与待办结构化列出，负责人/截止时间明确 |
| 纪要格式各写各的、颗粒度不一 | ③ 企业模板定制 | 按部门/会议类型套模板，口径统一、可检索 |
| 待办无跟进、纪要无沉淀 | ④ 分发到项目系统 + 沉淀知识库 | 行动项落成任务持续跟进，纪要走完可回溯 |

**设计原则：AI 不越权**——转写只做如实记录、不确定的发音/术语标出待人工确认；待办抽取只做"抽取 + 建议"，负责人与截止时间的最终确认权始终在人；纪要分发前需负责人审阅确认，不直接外发。

### 2.4 长尾与边界场景（枚举四问）

主流程之外，主动把复杂场景点出来，证明方案经得起生产追问：

1. **金额/数量异常**：多人发言口径不一、同一件事被重复陈述、会议跨时区——AI 给出结构化归并建议，最终口径由纪要负责人确认。
2. **数据/凭证异常**：录音不清晰、术语/英文/口音识别不确定、发言者不明——不确定处标出，由负责人回听补全，不臆造。
3. **权限/合规异常**：敏感议题、涉密信息、审计留痕——会议内容留在内网，纪要按权限分发，关键操作可追溯。
4. **流程/系统异常**：录音超长、上传失败、任务系统接口超时——自动分段处理，接口失败可重试并留痕，行动项落系统失败则提示人工兜底。

**能主动写出「哪些地方仍需人工」，是这套方案成熟度的标志。**

### 2.5 人机分工总表

| 环节 | AI 全自动 | AI 生成 + 人工确认 | 人工主导 |
|------|:---:|:---:|:---:|
| 语音转写、结构化分段 | ● | | |
| 结论/行动项/负责人抽取 | | ● | |
| 纪要模板套用与格式化 | ● | | |
| 行动项分发到项目系统 | ● | | |
| 纪要审阅与最终确认 | | | ● |
| 敏感议题的判断与脱敏 | | | ● |

这张表是整个方案的地基：**AI 负责「可自动化的整理与分发」，人负责「需要判断力的确认与决策」**。成员对 AI 纪要的信任，来自它知道自己不替人拍板、不替人下结论。

### 3.3 ROI 与回本周期

「值不值」要算得出来：**回本周期 = 一次性投入 ÷ 月净收益**，公开场景用区间与百分比表达，不写绝对金额：

| 类别 | 构成 |
|------|------|
| 一次性投入 | 软件授权 / License、服务器或云资源、实施与集成、纪要模板冷启动、培训 |
| 持续性投入 | 模型调用 / API 费用、运维人力、模板与规则更新 |
| 收益（钱） | 人力节省：纪要整理时间大幅下降，会议组织者与参会者把省下的时间还给产出 |
| 收益（折算） | 行动项遗漏减少带来的项目返工减少、决策可回溯带来的沟通与对齐成本下降 |

> 某互联网公司项目管理团队脱敏参考：一次性投入主要为授权 + 实施 + 纪要模板冷启动，月净收益来自纪要整理人力释放与待办遗漏减少，**预计 6-9 个月回本**；未计入跨部门沟通成本下降与决策可回溯价值，属保守估算。回本周期用区间表达、不承诺具体数值；正式交付时以企业自身数据实测为准，按月复测，用数据说话。

## 四、落地路径与运营

### 4.1 分阶段推进节奏

方案落地遵循「**先验证、再试点、后规模化**」，每阶段有明确动作和验收口径：

| 阶段 | 目标 | 典型动作 | 验收口径 |
|------|------|---------|---------|
| 验证 | 用真实样本证明核心链路可行 | 导入真实会议录音，测转写准确率、待办抽取完整率 | 各指标达到约定口径 |
| 试点 | 在一个会议高频的团队真跑 | 项目管理/产品团队上线，收集使用反馈 | 纪要耗时、待办完整率、分发成功率达到口径 |
| 规模化 | 全团队推广并接入业务系统 | 对接项目/任务系统，套用企业模板，全量上线 | 全量运行，待办跟进闭环，运营机制建立 |

> 具体周期和阈值视组织规模、数据条件与团队配合度调整；我们不承诺「一次上线、永久可用」，而是交付可持续运营的机制。

### 4.2 数据与规则冷启动

- 优先梳理**纪要模板、部门与会议类型、行动项字段**，这是结构化产出的地基；
- 先用小批量真实会议录音验证转写准确率，再增量补充术语库与历史纪要；
- 每批导入后人工抽检，纠错后回流，避免「错的数据越滚越大」。

### 4.3 持续运营闭环

- **转写纠错回流**：不确定的术语/发音被成员纠正后，回流优化术语库与转写效果；
- **模板迭代**：各部门补充新模板、修订旧模板，同步到结构化引擎；
- **效果复测**：按月复测转写准确率、待办抽取完整率，找出下滑原因；
- **知识沉淀更新**：纪要入库后持续沉淀，让历史决策可检索、可复用。

## 五、选型价值与下一步

### 5.1 FastGPT 企业级价值（能力 → 证据 → 收益）

我们交付的不是一个转写工具，而是一套跑得通、控得住、越用越准的会议纪要体系。它建立在这些企业级能力之上：

| 能力 | 证据 | 对会议纪要场景的收益 |
|------|------|----------------|
| 私有化部署，数据自控 | 系统部署在企业内网 | 会议内容不出网，满足保密与合规要求 |
| OpenAPI 完整开放 | 兼容 OpenAI 接口格式 | 对接飞书/钉钉/企微/项目系统，纪要嵌入现有工作入口 |

### 5.2 选型顾虑回应

这是本文最关键的一节，正面回答"飞书/钉钉都有 AI 纪要了，为什么还要单独做一套"：

- **对比平台自带 AI 纪要（飞书妙记 / 钉钉闪记等）**：这类"会议自带纪要"主要解决「转写」这一件事，且**使用额度有限**——免费额度通常按场次/时长消耗，超出后要订阅企业版，会议高频的团队成本会随用量上浮；**纪要格式固定**，颗粒度、字段、语气都按平台默认，无法按企业的模板与部门口径输出；**定制开发门槛高**，想改格式、接自己的 CRM/项目系统、按角色分发，要么做不到、要么得碰平台开放能力做定制开发，周期长、成本高、还受平台迭代影响。FastGPT 把"转写、结构化、定制、分发、沉淀"整条链放在自己手里，纪要模板、字段、联动系统全部可按需定制，数据留在内网。
- **对比自研方案**：自研需要 AI 工程师与数月研发周期；本方案基于成熟底座与可视化编排，由现有 IT 团队在数周内落地。
- **对比通用 AI 助手**：通用助手能"总结一段文字"，但做不到按企业模板结构化、行动项落成任务、按角色分发与权限管控。
