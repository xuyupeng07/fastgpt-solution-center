# 解决方案写作方法论 · 公开通用（解决方案中心）

> 定位：面向大众的**公开解决方案文章**，用来**吸引**潜在采购决策者、推动预约 POC，而不是对某个具体客户成单。适用解决方案中心所有公开案例（AI 报销助手、智能客服、合同审核、数据副驾驶等）。
> 目标一句话：**让读者觉得"这说的就是我，我想用我的数据验证一下"**，然后点预约。
> 配套：`fastgpt-expert` skill 的 `references/solution-center/articles.md`（Mermaid 语法与排版硬性约束、发布前校验脚本——排版与校验以它为准，本文只讲"怎么写对"的方法论）、`references/solution-center/fastgpt-value-messaging.md`（企业价值表达）。
> 与《解决方案写作方法论-私人定制.md》共享写作质感，本文只讲公开场景特有的东西。

---

## 一、先想清楚：公开文章和售前方案是两回事

写之前先判断这份材料是给谁、要什么结果。两条线很多原则是**相反**的：

| 维度 | 私人定制（售前） | 公开通用（解决方案中心） |
| --- | --- | --- |
| 读者 | 一个具体客户的高管/IT/采购 | 大众，浏览中的潜在采购决策者 |
| 目标 | 成单（拿下这一个客户） | 吸引 → 预约 POC → 转售前 |
| 数据来源 | 尽调客户真实数据 | 脱敏行业案例 + 保守估算 |
| "换客户名" | 换了就**失效**（证明定制到位） | 换了仍**成立**（证明通用可迁移） |
| 细节锚点 | 用客户真实岗位/系统/数字 | 用脱敏场景（某连锁零售/某三甲医院） |
| 渠道 | 只写客户正在用的 | 尽量全覆盖（企微/钉钉/飞书/小程序/公众号/Web/API） |
| ROI/回本 | 算这个客户的回本周期 | 给行业参考区间 + 百分比 |
| 篇幅 | 灵活（5 章可长） | 正文 1200-1800 字 |
| 结尾动作 | 下一步：进入 POC / 补齐材料 | 预约免费 POC（短 CTA） |
| 脱敏 | 不需脱敏自己，但隐藏他人客户数据 | 必须脱敏（隐去公司名、不写真名） |

> 记忆锚点：**私人定制要"换名失效"，公开通用要"换名仍成立"——但两者都必须"细节真实可信"。** 公开文章最大的陷阱，是把"通用"写成"空洞"：换名是成立了，但没有一个具体画面，读者代入不进去。

## 二、公开文章的 8 条成功标尺（先立标尺）

| # | 标准 | 反例 | 正例 |
| - | --- | --- | --- |
| 1 | **通用可迁移**：换行业/渠道，场景依然成立 | 只适配某一个系统/某一家公司 | "报销助手覆盖飞书、企微、钉钉、泛微 OA 等入口" |
| 2 | **真实可信**：脱敏案例有体量、有落地前后数据 | "显著提升效率" | "某连锁零售售后中心，首响 3 分钟 → 12 秒" |
| 3 | **对号入座**：决策者读痛点表能代入自己 | 痛点只有孤例 | "财务逐单人工审核、翻制度，异常靠抽查" |
| 4 | **能力可感知**：多渠道 + 长尾边界 + 系统对接，证明不是演示 | "支持多渠道"五个字 | "员工在飞书群 @机器人 问差旅标准，客户在公众号问订单进度" |
| 5 | **价值可拍板**：每个数字解释为什么变 + 对采购意味着什么 | "人力成本下降 80%"无机制 | "首响下降，因为 AI 直接检索知识库并溯源" |
| 6 | **行动可转化**：结尾推到"预约免费 POC"，不用生硬销售 | "立即购买" | "用你自己的业务数据验证前文落地效果" |
| 7 | **痛点一一解决**：每个痛点都有对应的方案模块，每个模块都消灭一个痛点，结果可感知 | "方案很全面、功能很多" | "制度分散 → 知识库问答；审核靠人肉 → 规则校验；逐条闭环" |
| 8 | **投入回报可算**：给 ROI 与回本区间，让"值不值"算得出来 | "降本增效，价值显著" | "人力成本下降 35%-55%，预计 6-9 个月回本" |

## 三、文章结构：沿用「5 章决策链」

公开文章沿用原始方法论的「5 章 + 摘要」决策链——**为什么做 → 做什么 → 值不值 → 怎么做 → 现在干嘛**——只把每章按"公开通用"的口径改写：

| 原始 5 章（决策链） | 公开文章章节 | 公开场景的改写重点 |
| --- | --- | --- |
| 执行摘要（半页，可选） | **概览（必写）** | 一句话定位 + 脱敏案例标签 + 3 个核心结果数字 + 落地证据前置 |
| 一、业务理解与痛点 | **一、场景洞察与痛点** | 用脱敏行业案例写痛点因链，让读者对号入座，而非写"这一个客户" |
| 二、解决方案设计 | **二、解决方案设计** | 多渠道×多系统 + 人机分工 + 现状/目标流程 + 长尾边界 |
| 三、落地价值与收益 | **三、落地价值与收益** | 保守数据 + 指标三件套 + ROI 与回本区间 + 对采购意味着什么 |
| 四、实施路径 | **四、落地路径与运营** | 知识库冷启动 + 验证→试点→规模化 + 持续运营（写轻，不展开项目计划） |
| 五、风险、边界与下一步 | **五、选型价值与下一步** | FastGPT 选型价值 + 竞品边界 + 顾虑回应 + 预约免费 POC |
| 附录：技术方案要点 | （并入五） | 私有化/权限/安全等顾虑用业务语言写，不单独成附录 |

```text
概览（半页）           ← 首屏吸引 + 落地证据前置
一、场景洞察与痛点      ← 为什么做（脱敏案例 + 痛点因链）
二、解决方案设计        ← 做什么（多渠道×多系统 + 长尾边界 + 人机分工 + 流程）
三、落地价值与收益      ← 值不值（保守数据 + 指标三件套 + ROI 与回本区间）
四、落地路径与运营      ← 怎么做（冷启动 + 分阶段 + 运营闭环）
五、选型价值与下一步    ← 现在干嘛（FastGPT 卖点 + 竞品边界 + 预约 POC）
```

- **文件头**：YAML frontmatter，`sidebar_position` 排序 + `name`（≤10 字）+ `description`（干什么 + 量化结果，≤120 字，优先百分比）。
- **字数**：正文 1200-1800 字（硬性 900-2200），图文互证：正文讲业务、表格做对比、图表承载指标。

> 变化点：原始「五、风险/边界」对公开文章不适用（没有"这一个客户"的风险），改成「选型价值 + 预约 POC」；附录的技术要点并入选型章。

## 四、公开场景特有的核心技法

### 4.1 脱敏行业案例法（通用感的关键）

公开文章没有"这个客户"，但有"这类客户"。用**脱敏行业标签**代替公司名，保留体量与结果，让读者对号入座：

- 某三甲医院门诊导诊、某区域医疗集团、某连锁零售企业、某制造集团、某互联网公司。
- 案例要含三件套：**体量 + 上线周期 + 落地结果**（如"日均 800-1500 次咨询，上线 3-6 周完成首轮验证"）。
- 禁止出现真实公司名、人名、病历号、订单号等可定位主体的信息。

### 4.2 保守数据补全（没有数据怎么办）

公开文章的目标是吸引预约，**允许用保守的行业估算补全数据**，而不是留空或反复追问（见 `articles.md` 数据生成规范）：

- 优先百分比与区间、避免绝对金额："下降 35%-55%"，不写"节省 800 万"。
- 数字绑定业务口径："门诊导诊咨询""售后 FAQ 首响"，不写"效率提升"。
- 宁可保守："下降 35%" 比 "下降 95%" 可信。
- 禁止出现"待替换""示例数据""用户未提供"等占位痕迹——文章必须像可发布成稿。

### 4.3 多渠道 × 多系统覆盖（通用感的第二关键）

公开文章要证明"不管你用什么入口，这套方案都能接"。把客户可能在用的入口都点到：

| 入口 | 接入方式 | 场景 |
| --- | --- | --- |
| 飞书 / 钉钉 / 企业微信 | API 接入机器人 | 内部协作、审批、群聊问答 |
| 微信公众号 / 微信个人号 | API / ClawBot | 客服、私域、服务号问答 |
| 小程序 / APP / 自研系统 | API 接入 | 业务后端、用户端 |
| Web 免登录窗口 / 门户 | 分享链接 / iframe / 登录门户 | 官网客服、团队统一入口 |
| 泛微 OA / ERP / CRM / 财务 / 工单等业务系统 | API / 插件对接 | 审批、报销、合同、订单、数据查询 |

> 两个维度分开看，缺一不可：**渠道**是"用户从哪进来问/办"（IM、微信生态、自有端、Web、API），解决**入口覆盖**；**系统**是"AI 要接谁的后端"（OA、ERP、CRM、财务、工单），解决**业务打通**。只有渠道没有系统，方案就成了"只有前台没有后台"的聊天框；只有系统没有渠道，员工又不知道从哪进。公开文章两个维度都要点到。

**写法要求**：不罗列"支持多渠道"，落到"同一套知识库和流程在背后复用"——"员工在飞书群里 @机器人 问差旅标准，客户在公众号里问订单进度，报销单据经泛微 OA 发起，用的都是同一套知识库与校验流程"。

### 4.4 长尾与边界场景（证明经得起生产追问）

公开文章最容易露怯的是"只写主流程 happy path"。主动把长尾场景点出来，反而证明这是生产级方案。**枚举四问**：

1. **金额/数量异常**：多币种、跨部门分摊、红冲退款、超额、批量提交？
2. **数据/凭证异常**：缺字段、识别不确定、口径冲突、重复提交？
3. **权限/合规异常**：敏感数据、越权、审计留痕、合规否决？
4. **流程/系统异常**：接口超时、回调失败、并发峰值、人工介入点？

对每一项给"AI 怎么做 + 人工怎么兜底"，落进人机分工表。**能主动写出"哪些地方仍需人工"，是文章成熟度的标志。**

### 4.5 FastGPT 企业价值表达（打消选型顾虑）

公开文章要把 FastGPT 讲成"企业 AI 应用底座"，不是又一个聊天机器人。每篇至少自然提及 5 项卖点，并按**"能力 → 证据 → 收益"**表达（完整卖点库见 `fastgpt-value-messaging.md`）：

- 企业 RAG / 知识工程、可视化工作流、私有化部署、权限隔离与审计、模型无关、多渠道发布、OpenAI 兼容、MCP 工具化、POC 到生产闭环。
- 例："私有化部署 → 敏感资料留在内网 → 满足合规要求，打消数据外流顾虑"。

### 4.6 竞品边界表达（通用指代，不点名）

公开文章可以谈选型，但**用通用指代、不出现竞品名、不攻击**：

- "商业 SaaS 客服""自研方案""通用 AI 助手""桌面 Agent"，不写"某竞品没有 X"。
- 只写"能力边界差异"与"适用场景"，用"更适合"不用"一定更强"。
- 结论落到"客户该怎么选"，不是"我们多厉害"。

### 4.7 痛点因链 + 指标三件套（共享技法，数据口径不同）

与私人定制共享，但数据用**脱敏/保守**而非客户真实值：痛点写成"现象 → 影响谁 → 根因"；每个数字写"落地前 → 落地后 → 为什么变"。

### 4.8 人机分工表 + 流程透视图（共享技法）

同私人定制：给一张"AI 全自动 / AI 生成+人工确认 / 人工主导"分工表；用业务语言画现状 vs 目标流程，不暴露工作流内部实现。

### 4.9 痛点一一对应解决（因果闭环，不能只"罗列"要"消灭"）

公开文章讲痛点最容易犯两种错：一是**只列痛点不解决**（列了一堆"财务累、员工烦"，方案却没接住），二是**方案和痛点对不上号**（模块很全，却没人说得清每个模块在治哪个病）。读者读完要能自己画出一条线：**每个痛点 → 对应哪个模块 → 解决后变成什么**。

**三条纪律：**

1. **痛点成表、方案成表，两表对齐**：痛点表每一行，都能在方案模块表里找到对应"解药"；方案表每一行，都能反向指回一个痛点。不允许"这个模块很强但没解决任何痛点"的孤岛模块，也不允许"这个痛点很痛但方案没接住"的悬空痛点。
2. **用"根因 → 方案 → 结果"三列闭环**，不用"现象 → 功能"两列罗列。
3. **结果可感知**：闭环最后一步落到一个可观察的变化（耗时/转接率/覆盖率/工时），不停在"能力上线"。

**脱敏示例（报销场景）：**

| 客户痛点（脱敏） | 方案模块 | 落地后的结果 |
| --- | --- | --- |
| 制度散在文件里、员工反复问财务 | 制度知识库问答 | 报销类咨询 AI 直接解决约 70%-85%，答案带出处 |
| 发票要素靠手填、常被打回 | 发票识别 + 自动填单 | 单张填单耗时约 3 分钟 → 1 分钟以内 |
| 财务逐单全审、翻制度靠记忆 | 规则校验引擎 | 财务从逐单全审转为只审异常单 |
| 重复/超标/疑似虚假靠抽查 | 全量校验 + 人工复核 | 违规拦截从抽查变为全量必查 |

> 记忆锚点：**痛点不落空、方案不空转、结果可感知**——三句话连成一条"痛点被消灭"的闭环。

### 4.10 ROI 与投入回报（让"值不值"算得出来）

公开文章没有"这一个客户"的预算，但要给"这类客户"一笔算得清楚的账——不是空喊"降本增效"，而是给一套**投入回报的估算框架 + 脱敏行业参考区间**，让采购评审对着自己的体量往里套。

**回本周期 = 一次性投入 ÷ 月净收益**，公开场景用区间与百分比表达，不写绝对金额：

| 类别 | 公开文章怎么写（脱敏 + 区间） |
| --- | --- |
| 一次性投入 | 软件授权 / License、服务器或云资源、实施与集成、知识库冷启动、培训——写"投入构成"，不写具体金额 |
| 持续性投入 | 模型调用 / API 费用、运维人力、知识更新——写"存在且可控"，让读者意识到不是一次买断 |
| 收益（钱） | 人力节省（减少的坐席 / 审核 / 文案 × 月薪）——写"减少 X 人 × 人月成本"的百分比口径 |
| 收益（折算） | 响应缩短带来的转化与满意度、合规全检避免的罚款与声誉损失、新人培训周期缩短——写百分比区间 |

**三条纪律（公开版）：**

1. **投入写全、收益写保守**：部署、实施、培训都算进投入，收益宁可低估，回报才可信。
2. **优先百分比与区间、不写绝对金额**：写"人力成本下降 35%-55%""预计 6-9 个月回本"，不写"节省 800 万"。
3. **给区间不给绝对值**：写"预计 6-9 个月回本"，不写"6 个月整回本"，留出数据与实施的不确定。

**脱敏示例（换数字即用）：**

> 某连锁零售售后中心：一次性投入主要为授权 + 实施 + 知识库冷启动，月净收益来自晚班坐席减少（6 人 → 2 人）与转接率下降释放的资深人力，**预计 6-9 个月回本**；未计入满意度提升带来的复购，属保守估算。

**落地位置**：ROI 框架放在「三、落地价值与收益」章；回本区间进概览的核心结果数字，让首屏就有"这笔账划得来"的印象。

## 五、插图与图片占位符规范

公开文章**图文互证**，三类图各司其职（模板与语法硬性约束见 `articles.md`）：

| 类型 | 承载什么 | 位置 |
| --- | --- | --- |
| 数据对比图（ECharts / 图片） | 前后对比、趋势、ROI/成本拆解、占比 | 概览、价值、场景 |
| Mermaid 流程图 | 业务流转、系统协同、批量处理管道 | 方案 |
| 界面截图 | 官方演示、系统真实画面 | 概览（落地证据前置） |

- 每篇 Mermaid ≥1；数据前后对比、趋势、ROI 拆解等图表优先用 ECharts 代码块（```echarts```，SSR 安全的客户端懒渲染）呈现，涉及真实金额或无法数值化时退化为「表格 + 图片占位」；截图占位放在概览首屏。

### 5.1 ECharts 配色规范（明暗主题统一）

数据图由 `src/components/ECharts` 渲染，配色由 `src/css/custom.css` 里随 `[data-theme]` 切换的 `--chart-*` 变量统一驱动，**与站点 Infima 主色同源**（主色即 `--ifm-color-primary`），作者**不写死颜色**：

**① 语义色 token**：在 `"color"` 字段写关键字，组件按当前明暗主题自动解析为具体色值。

| token | 语义（按含义用，不按好看用） | 亮色 | 暗色 |
| --- | --- | --- | --- |
| `primary` | 品牌主色：落地后 / 主值 / 主序列 | `#326dff` | `#7d9fff` |
| `success` | 正向 / 达成 / 达标 | `#16a34a` | `#4ade80` |
| `warning` | 预警 / 注意 / 待处理 | `#d97706` | `#fbbf24` |
| `danger` | 负向 / 亏损 / 盈亏平衡线 / 报警 | `#dc2626` | `#f87171` |
| `neutral` | 中性：落地前 / 对比基线 / 占位 | `#94a3b8` | `#64748b` |
| `violet` / `cyan` | 多序列辅助色 | `#7c3aed` / `#0891b2` | `#a78bfa` / `#22d3ee` |

**② 组件自动注入的默认外观**（作者无需写）：序列色板 `[primary, success, warning, danger, neutral, violet, cyan]`、文字色、坐标轴线、刻度、分割线、图例与副标题色；明暗切换时图表自动重绘，配色始终贴合当前主题。

**③ 三条纪律**：

1. **不写死 hex**：除确需自定义外，颜色一律用 token；写死 hex 会在暗色模式下刺眼不协调。
2. **语义色按含义用**：前后对比「落地前 = `neutral`、落地后 = `primary`」，亏损/负向 = `danger`，达成 = `success`；别为了"配色丰富"偏离语义。
3. **文字/轴线交给组件**：不要在 option 里写死 `textStyle.color`、`axisLabel.color`、`splitLine.lineStyle.color` 等，组件已按主题注入，写死反而破坏明暗一致性。

**④ 坐标轴名称的写法（避免裁切与重叠）**：`containLabel` 只兜住刻度标签、不兜轴名；轴名（`name`）默认 `nameGap` 只有 15，很容易与刻度数值重叠，或贴到画布边缘被裁掉。规范：

1. **轴名要短**：把"示意 / 非实际金额 / 区间"等解释放进 `title.subtext` 或正文，轴名只留量纲（如「累计净现金流」「上线后月份」）。
2. **X 轴名**：用 `nameLocation: "middle"` 居中，`nameGap` 给 `25~30`，并在 `grid.bottom` 留足空间（建议 `≥16%`），避免默认"右端"贴边被裁。
3. **Y 轴名能省则省**：指标名已在 `title.subtext` / 图例 / tooltip 里说明时，纵轴直接省略 `name`，避免竖排名称把 `grid.left` 撑大、图形整体右移不居中。确需保留时：保持默认 `nameLocation: "end"`（顶端）、`nameGap` 给 `45~55` 让开刻度数值（默认 15 会与"-100"这类数字重叠），并让 `grid.left` 与 `grid.right` 大致对称、再在左侧留足空间。
4. 容器默认高 400px；双网格/多图要主动给图例与轴名之间留空隙，不要挤满百分比。

示例（落地前后对比，不写死色值，明暗自动适配）：

```json
{
  "series": [
    { "name": "落地前", "type": "bar", "data": [3], "itemStyle": { "color": "neutral" } },
    { "name": "落地后", "type": "bar", "data": [1], "itemStyle": { "color": "primary" } }
  ]
}
```

### 5.2 占位符统一格式（交代"放什么图 + 怎么拿到图"）

凡是"一张图比一段话更清楚"的地方，都放占位符。占位符必须**同时写清两件事**：放什么图、怎么截图或制图。作者拿到文稿就能直接去补图，不用再猜：

```text
> 【插图占位：<图片名称>】
> 图片类型：架构图 / 流程图 / 人机分工图 / 数据对比图 / ROI 拆解图 / 界面截图 / 渠道示意图 / 部署拓扑图
> 图片内容：<这张图要表达什么，一句话>
> 获取方式：截图 或 制图
>   截图：FastGPT 哪个页面 → 哪个菜单 → 截哪个区域 → 是否脱敏
>   制图：画什么结构（流程图/架构图/泳道图用 Mermaid，数据图表用 ECharts 代码块）
```

**截图类怎么填（写清路径，让作者照着点）**：

| 目标界面 | 截图路径（页面 → 菜单 → 区域） | 表达什么 |
| --- | --- | --- |
| 知识库 | 知识库 → 数据集 → 上传文档 | 制度/FAQ 已入库、分块状态 |
| 编排画布 | 应用 → 工作流 → 编排画布 | 业务 SOP 已可视化编排（只截画布外观，不截节点参数） |
| 对话溯源 | 应用 → 调试预览，提一个业务问题 | 回答 + 原文出处同框，证明可溯源 |
| 发布渠道 | 应用 → 发布渠道 | Web/API/机器人/公众号等入口配置 |
| 运营仪表板 | 应用 → 数据统计 | 调用量/命中率/满意度曲线 |

**制图类怎么填（写清结构，让作者照着画）**：

| 图 | 结构 | 工具 |
| --- | --- | --- |
| 业务架构图 | 数据源 → 知识工程 → 能力层 → 渠道层，四层纵向 | Mermaid |
| 现状 vs 目标流程 | 两条泳道对比，标出"断点在哪、怎么接上" | Mermaid |
| 人机分工图 | AI 全自动 / AI 生成+人工确认 / 人工主导 三列 | 表格 / Mermaid |
| 部署拓扑图 | 内网隔离、系统对接、多入口 | Mermaid |

### 5.4 占位符纪律

1. **占位符不进入最终交付稿**：交付前必须全部替换为真实图或删除。
2. **截图脱敏**：不暴露真实公司名、员工姓名、订单号、发票号、内部系统名、API Key；有敏感信息打码或改用演示数据。
3. **图片一律加图注**："图 X：……"，与正文呼应。
4. **不截内部实现**：工作流节点参数、Prompt、API 路径、内部 ID 一律不入图；只截业务流程外观与结果画面。

## 六、写作质感与去 AI 味（与私人定制共享）

- **去 AI 味**：禁用"赋能/抓手/一站式/保驾护航/在当今……背景下"；把 AI 味改写成具体画面。
- **细节锚点**：每模块至少一处，落到角色/时间点/动作/入口/文件类型/复核动作。
- **真实感**：写冷启动爬坡、低置信度转人工、质检复核——保留"不完美"反而可信。
- **价值感**：每段回答"so what"，写完数字追问"对 CTO/CIO/采购意味着什么"。
- **文采**：长短句交替、动词具体化、每段一个焦点、首段钩子。

---

## 七、硬规则（对内/对外边界）

1. **对外不暴露内部实现**：不写工作流节点名、Prompt、API 路径、堆栈、内部 ID。
2. **不承诺不可控结果**：未经验证的准确率/效果写保守估算或"待 POC 验证"。
3. **竞品克制**：只写能力边界，不攻击、不点名、不"全面碾压"。
4. **脱敏**：不暴露公司名、人名、病历号、订单号、收入、客诉量等真实数据。
5. **POC 只做预约入口**：全文重点是落地效果与采购价值，末尾短 CTA 引导预约，不大篇幅讲 POC 流程。
6. **不写占位痕迹**：不出现"待替换""示例数据""用户未提供"。
7. **数字口径一致**：前后不矛盾，每个数字可解释、绑定场景。
8. **图片占位符可执行**：需要配图处放 `【插图占位】` 占位符，同时交代"放什么图 + 怎么截图/制图"（见五）；占位符是写作期工作痕迹，交付前必须全部替换为真实图或删除——与第 6 条"正文不留占位痕迹"不冲突。
