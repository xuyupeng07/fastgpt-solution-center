# 解决方案写作方法论 · 公开通用（解决方案中心）

> 定位：面向大众的**公开解决方案文章**，用来**吸引**潜在采购决策者、推动预约 POC，而不是对某个具体客户成单。
> 目标一句话：**让读者觉得"这说的就是我，我想用我的数据验证一下"**，然后点预约。
> 配套：`fastgpt-expert` skill 的 `references/solution-center/articles.md`（Mermaid 语法与排版硬性约束）、`references/solution-center/fastgpt-value-messaging.md`（企业价值表达）；配图生成见项目 skill `solution-illustration`。
> 与《解决方案写作方法论-私人定制.md》共享写作质感，本文只讲公开场景特有的东西。

---

## 一、先想清楚：公开文章和售前方案是两回事

写之前先判断这份材料是给谁、要什么结果。两条线很多原则是**相反**的：

| 维度 | 私人定制（售前） | 公开通用（解决方案中心） |
| --- | --- | --- |
| 读者 | 一个具体客户的高管/IT/采购 | 大众，浏览中的潜在采购决策者 |
| 目标 | 成单（拿下这一个客户） | 吸引 → 预约 POC → 转售前 |
| 数据来源 | 尽调客户真实数据 | 脱敏行业案例 + 保守估算 |
| "换客户名" | 换了就**失效**（证明定制到位） | 换了仍**成立**（证明通用可迁移） |
| 细节锚点 | 用客户真实岗位/系统/数字 | 用脱敏场景（某连锁零售/某三甲医院） |
| 渠道 | 只写客户正在用的 | 尽量全覆盖（企微/钉钉/飞书/小程序/公众号/Web/API） |
| 数据/图表 | 用真实尽调数据，图型按数据故事选 | 用脱敏保守数据，图型按数据故事选 |
| 篇幅 | 灵活 | 正文 1200-1800 字 |
| 结尾动作 | 下一步：进入 POC / 补齐材料 | 预约免费 POC（短 CTA） |
| 脱敏 | 不需脱敏自己，但隐藏他人客户数据 | 必须脱敏（隐去公司名、不写真名） |

> 记忆锚点：**私人定制要"换名失效"，公开通用要"换名仍成立"——但两者都必须"细节真实可信"。** 公开文章最大的陷阱，是把"通用"写成"空洞"：换名是成立了，但没有一个具体画面，读者代入不进去。

## 二、成功标尺（先立标尺）

| # | 标准 | 反例 | 正例 |
| - | --- | --- | --- |
| 1 | **通用可迁移**：换行业/渠道，场景依然成立 | 只适配某一个系统/某一家公司 | "报销助手覆盖飞书、企微、钉钉、泛微 OA 等入口" |
| 2 | **真实可信**：脱敏案例有体量、有落地前后数据 | "显著提升效率" | "某连锁零售售后中心，首响 3 分钟 → 12 秒" |
| 3 | **对号入座**：决策者读痛点表能代入自己 | 痛点只有孤例 | "财务逐单人工审核、翻制度，异常靠抽查" |
| 4 | **能力可感知**：多渠道 + 长尾边界 + 系统对接，证明不是演示 | "支持多渠道"五个字 | "员工在飞书群 @机器人 问差旅标准，客户在公众号问订单进度" |
| 5 | **价值可拍板**：每个数字解释为什么变 + 对采购意味着什么 | "人力成本下降 80%"无机制 | "首响下降，因为 AI 直接检索知识库并溯源" |
| 6 | **行动可转化**：结尾推到"预约免费 POC"，不用生硬销售 | "立即购买" | "用你自己的业务数据验证前文落地效果" |
| 7 | **痛点一一解决**：每个痛点都有对应的方案模块，每个模块都消灭一个痛点 | "方案很全面、功能很多" | "制度分散 → 知识库问答；审核靠人肉 → 规则校验" |
| 8 | **投入回报可算**：给 ROI 与回本区间，让"值不值"算得出来 | "降本增效，价值显著" | "人力成本下降 35%-55%，预计 6-9 个月回本" |
| 9 | **图文有故事**：每张图只讲一个能一眼看懂的故事，图型跟着数据走 | 六篇文章六张一模一样的图 | "出题用漏斗画'知识点→题目→审核'，导诊用桑基画'症状→科室'" |
| 10 | **骨架固定、血肉可变**：五章+三级编号+章标题各篇统一（美观），开场/图型/痛点/数字按选题定制（不重样） | 各篇的开场、图型、痛点、数字全是一个样 | "章标题都叫'场景洞察与痛点'没问题；但报告用瀑布、翻译用桑基、导诊用热力，开场和痛点各说各话" |

> 第 9、10 条是公开文章最常翻车的两条：**图表千篇一律、血肉千篇一律**。骨架统一是专业（第三章），但图型、开场、痛点、数字必须每篇不同，否则读者看一篇就不想看第二篇。

## 三、文章结构：骨架固定，血肉可变

### 3.1 骨架固定（美观的来源），血肉可变（不重样的来源）

公开文章要同时做到两件事：**目录整齐可扫（美观）** 和 **每篇不重样（不流水线）**。关键是分开「骨架」和「血肉」：

| | 是什么 | 该怎样 | 为什么 |
| --- | --- | --- | --- |
| **骨架** | 五章结构 + 三级编号 + 章标题 + 每章子节 | **完全固定** | 导航是给读者扫目录用的，整齐就是专业；结构统一不等于流水线 |
| **血肉** | 开场钩子、痛点因链、方案模块、图型、数字、案例、分析深度 | **按选题定制** | 千篇一律的味儿来自空话套话与浅，不来自整齐的编号 |

一句话：**结构统一是专业，内容雷同才是流水线。** 各篇目录长得一样没问题，读起来每一篇都要不一样。

### 3.2 标准五章骨架（照抄，只换血肉）

决策链五件事（为什么做 → 做什么 → 值不值 → 怎么做 → 现在干嘛）固定映射为五章，**章标题各篇完全统一**（平行名词短语），子节清单也固定：

```text
一、场景洞察与痛点
   1.1 为什么「主题」值得做 AI      ← 一段洞察：现状系统的"空位"在哪
   1.2 共性痛点因链                  ← 现象/影响谁/根因 表 + "层层递进"总结句
   1.3 适用条件                      ← bullet + "不满足先补齐"的负责任表述
二、解决方案设计
   2.1 总体蓝图                      ← 现状 mermaid + 目标 mermaid + 架构图占位
   2.2 多渠道 × 多系统覆盖            ← 表 + "两个维度分开看"解释 + "落到一个具体画面"例子
   2.3 痛点一一对应解决               ← 表 + "不是堆叠是链" + "AI 不越权"
   2.4 长尾与边界场景（枚举四问）      ← 四类异常 + 每类 AI/人工分工
   2.5 人机分工总表                  ← 表 + "这张表是地基" + 泳道图占位
三、落地价值与收益
   3.1 价值维度                      ← 价值维度/面向对象/价值主张 表
   3.2 量化框架（指标三件套）          ← 落地前→落地后→为什么变 表 + 主题专属图型
   3.3 ROI 与回本周期                 ← 公式 + 投入/收益表 + 脱敏区间（不画回本曲线）
四、落地路径与运营
   4.1 分阶段推进节奏                 ← 验证/试点/规模化 表
   4.2 数据与规则冷启动               ← 先梳理什么、怎么抽检回流
   4.3 持续运营闭环                   ← 纠错回流/规则迭代/效果复测 + 仪表板占位
五、选型价值与下一步
   5.1 FastGPT 企业级价值             ← 能力→证据→收益 表（≥5 项）
   5.2 选型顾虑回应                   ← 对比 SaaS/自研/通用（不点名）
   5.3 预约免费 POC                   ← 短 CTA，用自身数据验证
```

- **章标题统一**（各篇一模一样）：一、场景洞察与痛点 / 二、解决方案设计 / 三、落地价值与收益 / 四、落地路径与运营 / 五、选型价值与下一步。
- **子标题结构统一、可嵌主题**：如 `1.1 为什么费用报销值得做 AI`、`1.1 为什么报告生成值得做 AI`；三级编号 `一、`（H2）/ `1.1`（H3）/ `1.1.1`（H4）。

### 3.3 每节一个「洞察」+ 一个「过渡」（深度纪律）

每个小节不能只有一张表/一句话，必须走完三步，否则就是堆料、泛泛而谈：

1. **先给一个有观点的分析段**：这一节要解决什么、根子在哪、为什么是 AI 的空位——一针见血，不是复述现象。
2. **再用表/图/例子支撑**：用「现象/影响谁/根因」表、现状/目标 mermaid、数据图、脱敏例子把观点坐实。
3. **最后一句承上启下**：这一节解决完，自然引到下一节（如"三大根因层层递进，下面第二章逐一对应消灭"）。

判断一个节够不够深：把它的表/图删掉，剩下的文字还能不能独立讲清一个道理；不能，就是没写透。**字数不要省，宁可写透也不要点到为止。**

### 3.4 动笔前先写「选题卡」（血肉定制的开始）

骨架是照抄的，血肉是定制的。动笔前用一段话把这篇的"独一无二"定下来：

```text
1. 一句话定位：这个方案解决「谁」的「什么挣扎」？（越具体越好）
2. 一个故事主角：谁，在什么时刻，最痛？（用 TA 的处境开场）
3. 三个想让人记住的数字：哪三个数字最反常识、最有冲击力？
4. 一个开场钩子：场景冲突 / 反常识数字 / 真实对话 / 不做的代价？
5. 一张「必放图」：最值得用一张图讲清的「一个点」，落在哪种图型？
```

> 例（出题）——主角"周三晚 11 点还在出月考卷的数学老师"；钩子用场景冲突；必放图用「知识点→题目→审核→入库」的漏斗。例（翻译）——主角"对着译完就乱套的 Markdown 逐处还原排版的工程师"；钩子用反常识"翻译质量没问题，格式全乱套"；必放图用「结构保持」的桑基。

### 3.5 开场钩子库（血肉可变的第一处）

开场摘要的第一句是各篇的"指纹"，禁止每篇都用"XX 是每个组织都在跑的刚性流程"：

| 钩子类型 | 写法 | 适配选题 |
| --- | --- | --- |
| **场景冲突** | 把一个人在最狼狈时刻的处境写成开头 | 出题、批改、导诊（一线最痛） |
| **反常识数字** | 用一个违反直觉的数字开场，再解释为什么 | 报告、翻译 |
| **真实对话** | 用一段典型对话开场，让读者"听到"自己 | 导诊、批改、报销 |
| **不做的代价** | 先算一笔"不改会怎样"的账 | 合规、安全、成本类 |
| **流程漂流记** | 跟着一个东西走完它痛苦的全程 | 报告、报销、翻译 |

开场之后，正文统一走 3.2 的标准五章骨架，血肉（痛点、模块、图型、数字）按选题填。

### 3.6 固定与可变清单（不因求变而失控）

- **固定**：五章 + 子节清单 + 三级编号 + 章标题（平行名词短语）+ 六项硬要求（多渠道 / 多系统 / 多场景 / 痛点一一对应 / ROI / 配图占位）。
- **可变**：开场钩子、故事主角、痛点因链、方案模块、图型（各篇不重样）、具体数字、脱敏案例、分析切入角度。

变化的是**血肉怎么讲、讲多深**，不变的是**骨架长什么样、六件事一件不能少**。

## 四、核心技法

### 4.1 脱敏行业案例法（通用感的关键）

公开文章没有"这个客户"，但有"这类客户"。用**脱敏行业标签**代替公司名，保留体量与结果：

- 某三甲医院门诊、某区域教育集团、某连锁零售企业、某制造集团、某互联网公司。
- 案例含三件套：**体量 + 上线周期 + 落地结果**（如"日均 800-1500 次咨询，上线 3-6 周完成首轮验证"）。
- 禁止真实公司名、人名、病历号、订单号等可定位主体的信息。

### 4.2 保守数据补全（没有数据怎么办）

允许用保守的行业估算补全，不反复追问：

- 优先百分比与区间："下降 35%-55%"，不写"节省 800 万"。
- 数字绑定业务口径："门诊导诊咨询""售后 FAQ 首响"，不写"效率提升"。
- 宁可保守："下降 35%" 比 "下降 95%" 可信。
- 禁止"待替换""示例数据""用户未提供"等占位痕迹。

### 4.3 多渠道 × 多系统覆盖

不罗列"支持多渠道"，落到"同一套知识库和流程在背后复用"：

| 入口 | 接入方式 | 场景 |
| --- | --- | --- |
| 飞书 / 钉钉 / 企业微信 | API 接入机器人 | 内部协作、审批、群聊问答 |
| 微信公众号 / 微信个人号 | API / ClawBot | 客服、私域、服务号问答 |
| 小程序 / APP / 自研系统 | API 接入 | 业务后端、用户端 |
| Web 免登录窗口 / 门户 | 分享链接 / iframe / 登录门户 | 官网客服、团队统一入口 |
| 泛微 OA / ERP / CRM / 财务 / 工单等 | API / 插件对接 | 审批、报销、合同、订单、数据查询 |

> 渠道解决"用户从哪进来问/办"，系统解决"AI 要接谁的后端"。只有渠道没有系统 = 只有前台没有后台的聊天框；只有系统没有渠道 = 员工不知道从哪进。

### 4.4 长尾与边界场景（枚举四问）

主动把长尾场景点出来，证明经得起生产追问：

1. **金额/数量异常**：多币种、跨部门分摊、红冲退款、超额、批量提交？
2. **数据/凭证异常**：缺字段、识别不确定、口径冲突、重复提交？
3. **权限/合规异常**：敏感数据、越权、审计留痕、合规否决？
4. **流程/系统异常**：接口超时、回调失败、并发峰值、人工介入点？

对每一项给"AI 怎么做 + 人工怎么兜底"，落进人机分工表。**能主动写出"哪些地方仍需人工"，是文章成熟度的标志。**

### 4.5 FastGPT 企业价值表达

每篇至少自然提及 5 项卖点，按"能力 → 证据 → 收益"表达：企业 RAG / 知识工程、可视化工作流、私有化部署、权限隔离与审计、模型无关、多渠道发布、OpenAI 兼容、MCP 工具化、POC 到生产闭环。例："私有化部署 → 敏感资料留在内网 → 满足合规要求，打消数据外流顾虑"。

### 4.6 竞品边界表达

用通用指代（"商业 SaaS""自研方案""通用 AI 助手""桌面 Agent"），不点名、不攻击、不"全面碾压"；只写能力边界差异与适用场景，结论落到"客户该怎么选"。

### 4.7 痛点因链 + 指标三件套

痛点写成"现象 → 影响谁 → 根因"；每个数字写"落地前 → 落地后 → 为什么变"。

### 4.8 人机分工表

给一张"AI 全自动 / AI 生成+人工确认 / 人工主导"分工表，告诉客户"AI 做什么、人做什么、谁兜底"。

### 4.9 痛点一一对应解决（因果闭环）

**三条纪律**：① 痛点成表、方案成表，两表对齐（不允许孤岛模块、不允许悬空痛点）；② 用"根因 → 方案 → 结果"三列闭环，不用"现象 → 功能"两列；③ 结果落到可观察变化（耗时/转接率/覆盖率/工时），不停在"能力上线"。

### 4.10 ROI 与投入回报（让"值不值"算得出来）

给一套**投入回报的估算框架 + 脱敏行业参考区间**，让采购评审对着自己的体量往里套。

**回本周期 = 一次性投入 ÷ 月净收益**，公开场景用区间与百分比表达，不写绝对金额：

| 类别 | 公开文章怎么写 |
| --- | --- |
| 一次性投入 | 授权 / 服务器 / 实施集成 / 冷启动 / 培训——写构成，不写金额 |
| 持续性投入 | 模型调用 / 运维 / 更新——写"存在且可控" |
| 收益（钱） | 人力节省（减少的坐席 / 审核 / 文案 × 月薪）——百分比口径 |
| 收益（折算） | 响应缩短带来的转化、合规全检避免的罚款与声誉、培训周期缩短——百分比区间 |

**三条纪律**：① 投入写全、收益写保守；② 优先百分比与区间、不写绝对金额；③ 给区间不给绝对值（"预计 6-9 个月回本"，不写"6 个月整"）。

> **注意**：回本周期用**文字 + 表格**表达（如"预计 5-8 个月回本，未计入 X 属保守估算"）。**不要为回本周期画伪造的"累计净现金流"曲线图**——那个曲线是编出来的，既难估量又不诚实，见 5.3 第三条纪律。

## 五、图表与配图（第一性原理）

### 5.1 一张图的存在理由

**一张图只有在"让数字或流程的意义一眼可见"时才值得放**；否则就是占地、稀释正文。放图前先回答：

```text
这张图的一句话结论是什么？（读者看完图，脑子里只留下一句话）
如果没有这张图，读者会不会错过一个关键信息？
```

没有一句话结论 → 不放图。有结论 → 下面 5.2 选型。

### 5.2 图表选型：图型跟着「数据的故事」走

**图型由数据要讲的故事决定，不由清单决定。** 先定故事，再选图型。常见故事与对应图型（含本项目方案可用的例子）：

| 数据的故事 | 首选图型 | 本项目示例 |
| --- | --- | --- |
| 分类对比（谁高谁低） | 柱状图 / 横向条形图 | 各渠道咨询量对比、各科室导诊量对比 |
| 随时间变化（趋势/爬坡） | 折线图 / 面积图 | 上线后 N 个月效率/采纳率爬坡曲线 |
| 构成 / 占比 | 饼图 / 环形图 | 老师时间花在哪、翻译成本构成、财务审核时间分配 |
| 多维打分（多个维度谁强谁弱） | 雷达图 | 方案在「效率/成本/质量/覆盖」四维的评估 |
| 转化 / 流失（漏斗） | 漏斗图 | 出题：知识点→生成→审核→入库；导诊：咨询→分诊→挂号→就诊 |
| 来源去向 / 流转（谁流向谁） | 桑基图 | 多渠道（企微/钉钉/公众号）→ 能力 → 系统（OA/ERP/HIS） |
| 相关 / 分布（两者关系） | 散点图 | 处理时长 vs 满意度、题量 vs 老师耗时 |
| 累积桥接（从 A 怎么一步步到 B） | 瀑布图 | 从「现状耗时」减掉各模块节省，一步步落到「目标耗时」 |
| 强度 / 矩阵（横纵两个维度的密度） | 热力图 | 各科室 × 各时段的门诊咨询强度 |
| 排名（Top N 谁最靠前） | 横向条形图 | 高频问题 Top N、耗时最高的环节 Top N |

**选型三步**：① 先写「这张图的一句话结论」；② 看结论落在上表哪种"故事"；③ 用对应图型，数据取自 4.2 的保守估算。**同一篇文章里，图型不要重复**——有了一张柱状图，下一张就换漏斗或桑基或雷达。

### 5.3 图表三条纪律（硬性）

1. **图型跟着故事走，禁止固定图型**：不允许"每篇都放一张前后对比柱状图 + 一张回本曲线"这种流水线。六篇文章六种图，才是达标。
2. **数据真实可信，禁止伪基线**：不允许"落地前 = 0"这种假数据——"落地前靠手工"是定性、不是 0。没有真实"前"值，就换一种图（占比/构成/漏斗/桑基/热力），别硬凑前后对比。
3. **禁止伪造"回本周期"曲线图**：回本周期很难估量，画一条"逐月累计净现金流"曲线等于编造数字。回本周期用文字 + 表格（见 4.10）表达；要配图，改用**瀑布图**讲"从投入如何一步步累积到净收益的构成"，或**环形图**讲"一次性投入 vs 持续投入 vs 收益"的结构——讲得清、算得出，才画得诚实。

### 5.4 ECharts 配色规范（明暗主题统一）

数据图由 `src/components/ECharts` 渲染，配色由 `src/css/custom.css` 的 `--chart-*` 变量驱动，与站点主色同源，作者**不写死 hex**。

**语义色 token**（按含义用，不按好看用）：

| token | 语义 | 亮色 | 暗色 |
| --- | --- | --- | --- |
| `primary` | 品牌主色：落地后 / 主值 / 主序列 | `#326dff` | `#7d9fff` |
| `success` | 正向 / 达成 / 达标 | `#16a34a` | `#4ade80` |
| `warning` | 预警 / 注意 / 待处理 | `#d97706` | `#fbbf24` |
| `danger` | 负向 / 亏损 / 报警 | `#dc2626` | `#f87171` |
| `neutral` | 中性：基线 / 对比 / 占位 | `#94a3b8` | `#64748b` |
| `violet` / `cyan` | 多序列辅助色 | `#7c3aed` / `#0891b2` | `#a78bfa` / `#22d3ee` |

**三条纪律**：① 不写死 hex；② 语义色按含义用（落地前=`neutral`、落地后=`primary`、负向=`danger`、达成=`success`）；③ 文字/轴线交给组件，不写死 `textStyle.color`、`axisLabel.color`、`splitLine.lineStyle.color`。

**轴名写法**：轴名要短（解释放 `title.subtext`）；X 轴 `nameLocation:"middle"`、`nameGap` 25~30、`grid.bottom ≥16%`；Y 轴能省则省，确需保留时 `nameLocation:"end"`、`nameGap` 45~55；容器默认高 400px。

### 5.5 配图占位符规范

凡是"一张图比一段话更清楚"的地方放占位符，**同时交代放什么图 + 怎么截图/制图**：

```text
> 【插图占位：<图片名称>】
> 图片类型：架构图 / 流程图 / 人机分工图 / 数据图（写明图型）/ 界面截图 / 渠道示意图
> 图片内容：<这张图要表达什么，一句话>
> 获取方式：截图 或 制图
>   截图：FastGPT 哪个页面 → 哪个菜单 → 截哪个区域 → 是否脱敏
>   制图：画什么结构（Mermaid / ECharts 图型 / SVG）
```

**截图类**：知识库（知识库 → 数据集 → 上传文档）、编排画布（应用 → 工作流 → 编排画布，只截外观不截节点参数）、对话溯源（调试预览 + 原文出处同框）、发布渠道（应用 → 发布渠道）、运营仪表板（应用 → 数据统计）。

**制图类**：业务架构图（数据→知识→能力→渠道四层，Mermaid）、现状 vs 目标流程（两条泳道，Mermaid）、人机分工图（三列，表格/Mermaid）、数据图（按 5.2 选型，ECharts）。

**必放占位符的位置**（每类至少一张，图型按选题换）：

| 位置 | 图 | 建议 |
| --- | --- | --- |
| 概览首屏 | 界面截图 + 演示视频 | 官方演示 + 系统真实画面 |
| 二、方案 | 业务架构图 | 数据 → 知识 → 能力 → 渠道分层 |
| 二、方案 | 现状 vs 目标流程图 | 断点在哪、怎么接上 |
| 二、方案 | 人机分工图 | 谁全自动、谁确认、谁主导 |
| 三、价值 | 数据图（按 5.2 选型） | 一句话结论 + 对应图型 |
| 五、选型 | 界面截图 | 私有化部署、权限配置、发布渠道页 |

**占位符纪律**：占位符不进最终交付稿，交付前替换为真实图或删除；截图脱敏；图片一律加图注（"图 X：……"）；不截内部实现（节点参数、Prompt、API 路径、内部 ID）。

## 六、写作质感与去 AI 味

- **去 AI 味**：禁用"赋能/抓手/一站式/保驾护航/在当今……背景下"；把 AI 味改写成具体画面。
- **细节锚点**：每模块至少一处，落到角色/时间点/动作/入口/文件类型/复核动作。
- **真实感**：写冷启动爬坡、低置信度转人工、质检复核——保留"不完美"反而可信。
- **价值感**：每段回答"so what"，写完数字追问"对 CTO/CIO/采购意味着什么"。
- **生动性**：长短句交替、动词具体化、每段一个焦点、首段钩子、让具体的人开口说话。

---

## 七、硬规则（对内/对外边界）

1. 对外不暴露内部实现（工作流节点名、Prompt、API 路径、堆栈、内部 ID）。
2. 不承诺不可控结果（未经验证的准确率写保守估算或"待 POC 验证"）。
3. 竞品克制（只写能力边界，不攻击、不点名、不"全面碾压"）。
4. 脱敏（不暴露公司名、人名、病历号、订单号、收入、客诉量）。
5. POC 只做预约入口（全文重点是落地价值，末尾短 CTA，不展开 POC 流程）。
6. 不写占位痕迹（不出现"待替换""示例数据""用户未提供"）。
7. 数字口径一致（前后不矛盾，每个数字可解释、绑定场景）。
8. 图片占位符可执行（交代放什么图 + 怎么截图/制图，交付前替换或删除）。
9. **禁止固定图型**（六篇文章六种图，图型跟着故事走）。
10. **禁止伪基线**（"落地前 = 0"这类假数据一律不用）。
11. **禁止伪造回本曲线**（回本周期用文字+表格，不画累计净现金流曲线）。
12. **骨架固定、血肉可变**：五章 + 三级编号 + 章标题各篇统一（见 3.2），但开场、图型、痛点、数字按选题定制，各篇血肉不许长成一个样。

## 八、对抗性自测（发布前红队）

写完先把自己当成一个不耐烦的企业采购决策者，问三个"扫一眼就关掉"的问题：

1. **扫一眼目录，我想点进去吗？** 章标题各篇统一（场景洞察与痛点 / 解决方案设计…）是应该的；要警惕的是「血肉」重样——如果各篇的开场、图型、痛点例子、数字也长成一个样，才是真流水线。目录整齐 + 血肉各异 = 专业且耐读。
2. **扫一眼图，六篇是不是同一张？** 如果图都是"前后对比柱状图 + 回本曲线"，说明图表模板化了；回到 5.2 按故事重新选型。
3. **读第一段，我会读第二段吗？** 如果第一段是"XX 是每个组织都在跑的刚性流程"，说明开场模板化了；回到 3.3 换钩子。

**红队三连问（模拟读者追问）**：

- "你说的这个数字，我怎么信？" → 数字有没有绑定口径、解释机制、标注保守估算？
- "这跟我有什么关系？" → 有没有一个具体的人的具体处境让读者对号入座？
- "看完这一篇，为什么还要看下一篇？" → 下一篇的开场、图型、痛点、数字是不是跟前一篇不一样？

> 原则：**目录长成一个样，血肉长成各不相同的样；每一篇都要有自己的指纹——一个钩子、一张必放图、一组反常识数字。**

## 九、交付前检查清单（自检）

```text
□ 这是给"大众吸引"还是"对客成单"？走的是公开通用这条线吗？
□ 换掉行业名/渠道，方案是否依然成立（通用可迁移）？
□ 是否用了脱敏行业案例（体量 + 上线周期 + 落地结果），无真实公司名？
□ 数据是否保守可信（百分比/区间、绑定场景、不出现"待替换/示例数据"）？
□ 是否覆盖多渠道/多系统入口，并说明同一套能力复用？
□ 是否用枚举四问写清长尾与边界场景的 AI 与人工分工？
□ 每个数字是否解释了"为什么变" + "对采购意味着什么"？
□ 是否至少提及 5 项 FastGPT 卖点，按"能力→证据→收益"表达？
□ 竞品是否用通用指代、不点名、不攻击？
□ 是否有人机分工表 + 现状/目标流程图（业务语言，不暴露内部实现）？
□ 痛点是否一一对应解决（每痛点有解药、每模块有对应痛点、结果可感知）？
□ 是否给了 ROI 与回本区间（投入写全、收益写保守、给区间不给绝对值）？
□ 【图表】每张图有没有"一句话结论"？图型是不是跟着数据的故事走（见 5.2）？
□ 【图表】图型是否多样（不是清一色前后对比柱状图）？
□ 【图表】有没有伪基线（"落地前 = 0"）？有没有伪造的回本曲线？
□ 【结构】是否先写了"选题卡"（一句话定位 + 故事主角 + 三个数字 + 钩子 + 必放图）？
□ 【结构】开场是否用了钩子库的某一种，而非"XX 是刚性流程"套话？
□ 【结构】章标题是否各篇统一（平行名词短语），子标题是否按标准清单嵌主题？
□ 【深度】每个小节是否走「洞察段 → 表/图/例 → 承上启下」三步，删掉图表后文字还能独立讲清一个道理？
□ 每个图片占位符是否交代了"放什么图 + 怎么截图/制图"，并标注图注与脱敏？
□ 结尾是否用短 CTA 引导"预约免费 POC"，而非生硬销售话术？
□ 是否删除了内部实现细节、内部话语与占位痕迹？
□ 字数是否在 900-2200 字（推荐 1200-1800）？
□ 对抗性自测三问（目录想点 / 图不重样 / 第一段想读）是否通过？
```
